## 2. Цель и бизнес-задача

Ежемесячно выбирать абонентов с наибольшим риском расторжения договора в ближайший месяц, чтобы отдел удержания связался с ними до ухода. Кампания ограничена: **не более 10 % активной базы** на дату расчёта.

Критерий успеха — доля ушедших абонентов, попавших в список кампании (Recall@10 %), заметно выше бейзлайна по простому правилу и выше случайного выбора (≈10 %).

Вне рамок: расчёт экономики удерживающих предложений, выбор конкретного предложения, A/B-тест кампании.

## 4. Определение оттока (целевая переменная)

**Отток** — расторжение договора: в `contract_events.csv` есть событие `event_type = termination` с `event_date` в интервале **[t, t + 1 календарный месяц)**, где t — дата расчёта.

```
churn(i, t) = 1, если ∃ termination: customer_id = i и t ≤ event_date < t + 1 мес.
churn(i, t) = 0 иначе (для абонента из активной базы на t)
```

Проверка: поле `event_type` и `event_date` журнала событий. Журнал полон до 01.10.2026, у абонента не более одного расторжения и нет повторных подключений, поэтому событие однозначно.

**Не считаются оттоком** (используются только как признаки): нулевая оплата, рост долга, нулевой или пропущенный трафик, понижение тарифа, неполный месяц `active_days`. По README и данным это не равно расторжению.

## 5. Дата расчёта, горизонт, активная база

- **Дата расчёта t** — 00:00 МСК первого числа месяца. К этому моменту доступен биллинг по предыдущий месяц включительно (`available_at = billing_month + 1 мес.`, проверено на всех строках).
- **Горизонт** — календарный месяц `[t, t + 1 мес.)` (28–31 день). Совпадает с циклом биллинга и ежемесячной кампанией; для t = 01.09.2026 это ровно 30 дней из примера README.
- **Активная база на t**: `activation_date < t` и (`termination` нет или `termination_date ≥ t`). Дата подключения берётся из журнала событий: в справочнике 65 пропусков, остальные совпадают с журналом.
- **Новые абоненты** (короткая история) **включаются** в базу и в знаменатель лимита 10 %. Отсутствующие ранние месяцы — пропуск, не ноль; добавляются признаки `tenure_days` и `n_history_months`. Исключать ли их из обзвона — вопрос заказчику (В3).

### Схема срезов

| Назначение | Даты расчёта t | Исход наблюдается |
|---|---|---|
| Обучение | 01.12.2025 … 01.07.2026 (8 срезов) | да |
| Валидация | 01.08.2026 | да |
| Тест (финальная оценка) | 01.09.2026 | да, [01.09, 01.10) |
| Боевой прогноз | 01.10.2026 | нет — исход за пределами выгрузки |

Разбиение только по времени: горизонт любого обучающего среза заканчивается не позже даты следующего контрольного среза. Срезы 10–11.2025 не используются для обучения из-за 1–2 месяцев истории, но могут войти в анализ.

### Факты по срезам (из аудита)

| t | Активная база | Ушло за горизонт | Доля, % | Лимит 10 % |
|---|---|---|---|---|
| 01.12.2025 | 1969 | 48 | 2,44 | 196 |
| 01.08.2026 | 1929 | 63 | 3,27 | 192 |
| 01.09.2026 | 1916 | 65 | 3,39 | 191 |
| 01.10.2026 | 1901 | ? | — | 190 |

Отток растёт с 2,2 % до 3,4 % в месяц; классы несбалансированы (≈1 : 30). Лимит кампании в 3 раза больше числа уходящих, поэтому ключевая метрика — полнота в пределах лимита.

## 6. Доступные сведения и будущие события

| Доступно на дату t (признаки) | Будущее относительно t (только для целевой переменной и проверки) |
|---|---|
| Строки биллинга с `available_at ≤ t`, т. е. месяцы до t | Биллинг за месяц t и позже |
| Регион, канал, сегмент абонента | События `termination` с датой ≥ t |
| Дата подключения → стаж, длина истории | Подключения после t (новые абоненты не входят в базу) |
| Производные: тренды трафика/минут, задержки оплаты, долг на конец последнего месяца, смены тарифа, понижение тарифа | Факт наличия абонента в итоговом справочнике / «итоговый статус» |
| Обращения в поддержку с моментом поступления в хранилище ≤ t (когда появятся) | Обращения после t, в т. ч. заявление о расторжении |

Правила против утечки: фильтр по `available_at`, а не по `billing_month`; признаки считаются отдельно для каждого t; строка месяца расторжения (634 строки с неполным `active_days`) не попадает в признаки, т. к. доступна только после t. Проверки закреплены в `tests/test_target.py`.

## 7. Выход решения

Ежемесячно на дату t — таблица по всей активной базе:

| Поле | Описание |
|---|---|
| `customer_id` | абонент |
| `snapshot_date` | дата расчёта t |
| `churn_score` | оценка вероятности расторжения в [t, t + 1 мес.) |
| `rank` | место по убыванию риска |
| `in_campaign` | 1 для первых N = ⌊0,10 × размер базы⌋ абонентов (на 01.10.2026: N = 190) |
| `top_factors` | 2–3 главных фактора риска для оператора |
| `model_version` | версия модели и данных |

Ограничение кампании — жёсткое: `in_campaign` никогда не превышает 10 % базы; если заказчик исключит новых абонентов или сегмент, лимит считается от всей активной базы, а исключённые пропускаются.

## 8. Метрики качества

- **Основная:** Recall@10 % — доля ушедших за горизонт, попавших в `in_campaign`.
- **Дополнительно:** Precision@10 %, Lift@10 % (относительно доли оттока), PR-AUC (дисбаланс классов), стабильность по срезам.
- **Бейзлайны:** случайный выбор (Recall ≈ 10 %); правило «долг на конец месяца > 0 или задержка оплаты, затем по сумме долга»; логистическая регрессия.

## 9. Допущения, вопросы, риски

Список вопросов заказчику и принятых допущений — `docs/questions_and_assumptions.md`. Ключевые риски:

| Риск | Мера |
|---|---|
| Утечка будущего в признаки | Срез по `available_at`, тесты, разбиение по времени |
| Малый объём (≈65 случаев оттока в тесте) | Доверительные интервалы метрик бутстрепом, несколько срезов обучения |
| Дрейф: доля оттока растёт | Оценка по последним срезам, мониторинг на боевом срезе |
| Короткая история у новых абонентов | Пропуски + `n_history_months`, отдельная проверка качества на подгруппе |
| Обращения могут содержать заявление о расторжении | Исключить категорию или проверить, что обращение раньше t |
| Команда 2 человека | Совмещение ролей, перекрёстная проверка |
