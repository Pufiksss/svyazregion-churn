# СвязьРегион: итоговая проверка качества

Команда: Милузов Алексей, Акентьев Захар. Этап 6.

## Задача

На 00:00 МСК первого числа ранжируем активных абонентов по риску расторжения договора в начинающемся календарном месяце. В кампанию попадает не более 10% базы; высокая оценка риска не означает, что контакт предотвратит уход.

## Короткий протокол

Правила сохранены в `protocol.json` до первого расчёта test в этом этапе.

| Что фиксируем | Значение |
|---|---|
| Выбранная модель | `exp04_hgb_leaf7`, `../5_model/models/candidate.joblib`. Максимальный validation Recall@K по правилу этапа 5; при равенстве AP, затем порядок опытов. Нового выбора на этапе 6 нет. |
| Test и исход | T = 01.09.2026 00:00 МСК. `termination` в [01.09.2026, 01.10.2026). Горизонт полностью наблюдается. База по прежнему уставу: `activation < T`, нет расторжения или `termination >= T` (состояние перед событиями на T). |
| Правило сравнения | Одинаковая база; K = floor(0,10 × N), равные score по `customer_id` по возрастанию. Baseline: долг прошлого месяца по убыванию; неизвестный долг получает score -1 и идёт после известных, без восстановления значения. |
| Метрики | Recall@K = найдено/ушли; Precision@K = найдено/K. Рядом N, K и количества. Validation перенесена из этапа 5, test рассчитан здесь. AP приведена дополнительно, не меняет правило выбора. |
| Использовали test для выбора? | Нет в этом расчёте: применён ранее сохранённый кандидат, без fit, изменения признаков, параметров, порога или состава кампании по test. `test_used=false` в паспорте этапа 5; более раннее использование test вне представленных материалов проверить невозможно. |

## Запуск

Расчёт начинается от подготовленных признаков этапа 4. Исходные данные и обучение заново не запускаются. Расположите папку `6_final` рядом с существующими `4_features` и `5_model`.

Входы:
- `../4_features/output/features.csv`, `labels.csv`, `split.csv`;
- `../5_model/models/candidate.joblib`;
- `../5_model/output/metrics_summary.csv`, `validation_predictions.csv`.

Из папки `6_final`, Python 3.12 или 3.13:

```bash
python -m venv .venv
```

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Затем:

```bash
python -m pip install -r requirements.txt
python run_final.py
python -m pytest -q
```

Ожидаемый результат: validation 14/63 и 20/63; test 30/65 и 29/65 (baseline и модель). При несовместимых версиях, изменении входов или расхождении validation запуск останавливается. Фиксация входов учитывает CRLF/LF для текстовых файлов; бинарная модель сверяется побайтно.

Выходы в `output/`:

| Файл | Содержание |
|---|---|
| `metrics.csv` | Единая таблица validation/test |
| `test_model_predictions.csv`, `test_baseline_predictions.csv` | Вся база: ключи, score, rank, selected |
| `test_model_contacts.csv`, `test_baseline_contacts.csv` | Только выбранные 191 контакт |

`rank` начинается с 1, `selected=True` означает попадание в общий список K. Score модели является оценкой риска; его калибровка отдельно не проверялась. Score baseline равен сумме долга в рублях и не является вероятностью. Метки не используются в вычислении score.

На validation модель находила на 6 уходов больше baseline; на test она нашла на 1 меньше. Разница Recall модели минус baseline изменилась с +9,52 до -1,54 процентного пункта. AP на test: модель 0,1471, baseline 0,1166; преимущество AP не заменяет основной критерий кампании.

Это описательное сравнение одного месяца, не доказательство причины различий; 8 из 12 не следует обобщать на будущие месяцы. Таблица не используется для изменения кампании, квот или выбора модели.

## Три признака

| Признак | Смысл и возможная связь с уходом | Основание и ограничение |
|---|---|---|
| `debt_prev_rub` | Долг на конец предыдущего месяца, известный на T; финансовая нагрузка может сопровождать отказ от услуг. | EDA: 7,54% ухода при долге против 1,36% без долга, +6,18 п.п.; кластерный bootstrap ДИ [5,31; 7,06] п.п. Связь не доказывает причинность или важность внутри HGB. |
| `tenure_days` | Дни от подключения до T; у новых абонентов может отличаться опыт использования и устойчивость отношений с оператором. | EDA: <90 дней 3,65%, >=90 дней 2,74%; ДИ разницы [-0,19; 2,12] п.п. включает ноль. Уверенного подтверждения различия нет; признак непрерывный. |

## Вывод заказчику и два главных ограничения

Сохранённый HGB на test нашёл 29 из 65 уходов (Recall 44,62%, Precision 15,18%); правило долга при тех же 191 контакте нашло 30 (46,15% и 15,71%). Августовское преимущество не сохранилось. На дополнительной временной проверке этапа 5 baseline также находил 74 ухода против 70 у HGB.

1. **Ограниченный временной охват:** один test-месяц и 65 уходов не подтверждают устойчивость будущего качества; различие в один уход невелико. По test не заявляем статистическую значимость победы какого-либо подхода.
2. **Учебные данные и отсутствие проверки воздействия:** синтетическая база не доказывает перенос на реального оператора, а найденный уход не равен предотвращённому уходу. Без стоимости контакта, предложений и результатов кампании денежный эффект не рассчитывается.

**Действие:** зафиксировать HGB как проверенного кандидата этапа 5 и отсутствие подтверждённого преимущества. Оснований внедрять его вместо простого правила пока нет. Сохранить baseline как рабочий ориентир; проверить оба фиксированных подхода на новых периодах и реальных данных, затем отдельно проверить эффект кампании. Итоговый кандидат не заменяется новым победителем по test и не перенастраивается на сентябре.

Дополнительная известная оговорка сохранённой версии: в цифровом статусе `not_published_at_T` и `no_row` различаются по полной выгрузке, хотя для строгого исторического применения нужен единый статус недоступности или отдельный реестр ожидаемых отчётов. На существующих снимках `no_row` не встречался. Чтобы не менять оцениваемую модель после фиксации, в этапе 6 прежние признаки и Pipeline сохранены; исправление требует отдельной версии и нового протокола оценки.

## Проверки и воспроизводимость

При запуске выполняются: общая база/ключи и K; загрузка прежнего Pipeline без fit и без подбора; повторная загрузка тех же весов на тех же входах с точным совпадением score, рангов, top-K и метрик. 14.11.2026 повтор совпал. Это проверка воспроизводимости, а не доказательство качества на будущих данных.

Модель и её файл не изменены. Проверено воспроизведение прежних validation-прогнозов с точностью 1e-12. Исторические даты без зоны трактуются как МСК; в стартовом `evaluation_utils.py` исправлена интерпретация таких дат, чтобы конец горизонта 01.10 00:00 МСК не считался ошибочно 01.10 00:00 UTC.
